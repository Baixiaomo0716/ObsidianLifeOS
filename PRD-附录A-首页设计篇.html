第 1 章目标与边界

这一篇要解决一个具体问题：用户每天打开这个系统，看到的第一个界面长什么样，填完的东西又落到哪去。

范围内容
本篇覆盖首页四段结构、顶栏、今日速记、领域入口与列表视图、最近动态、记账数组落盘、日记与记账的关联、附件存储、入口与启动行为
本篇不覆盖其他领域表单的字段定义（见 PRD 第 6 章 6.3–6.6）、游戏化数值体系（v3.0）、设置页细节、初始化向导

承接的设计前提

以下四条来自 PRD 已定稿部分，本篇不再论证，直接沿用：

  • 定位——全生活记录系统，时间轴 / 生活 / 知识 / 行动四个领域等重并列
  • 落盘触发——有记录才建文件，不产生空白文件
  • 数据规范——type / category / status / created / updated 沿用既有体系
  • 格式即契约——DP-09：枚举与表格类字段格式一经写入即为契约，变更须走修订流程

第 2 章首页结构总览

首页由四段构成，从上到下按使用频次排列，而不是按领域排列——高频的在最上面，低频的收进入口。

段职责关键规则
1 · 顶栏时间定位与当日概览日期可切换，支持补记
2 · 今日速记每日高频录入可配置区块，各卡片独立保存
3 · 领域入口进入四领域四卡等重，点击进入插件内列表视图
4 · 最近动态近期提交一览跨表单最近 10 条，按更新时间倒序
贯穿全篇的一条总机制

首页按「表单是否已实现 + 用户是否勾选」渲染。

这条机制让首页只需设计一次，三个版本共用，不改一行代码：

版本已实现的表单首页自动呈现为
v1.0日记顶栏 + 日记卡 + 仅「时间轴」可用的领域入口 + 最近动态
v1.5+ 记账、任务长出记账卡与待办清单；最近动态出现多条来源
v2.0+ 旅游 · 娱乐 · 知识库 · 项目四领域入口全部可用，最近动态覆盖全部表单

第 3 章顶栏规格

三个指标

元素说明
系统名固定显示 LifeOS；点击回到今天
日期切换← 2026-09-28 周一 →，左右箭头逐日切换
当日支出显示所查看日期的记账合计；支出带负号展示，收入不带
连续记录连续记录 N 天，始终以今天为基准，不随日期切换变化
为什么顶栏只放三个

顶栏是唯一"每次打开都会看到"的区域。指标一旦超过三个，人会停止阅读它——那时它就从信息退化成装饰。不加本月结余、不加待办数。

连续记录天数的计算规则

日记或记账任一有记录，当天即算「已记录」。

理由：这个指标的作用是鼓励"每天来记点什么"，不是考核你写没写日记。门槛定太高，数字会很快断掉，然后它就失去意义了。

补记规则

规则内容
可切换范围只能向前回看，不能选未来
不选未来的理由记录的本质是"已经发生的事"，系统不需要未来的日记。允许选未来只会让人误把今天的账记到明天
切换后的变化顶栏「当日支出」→ 改显示该日合计；日记卡 → 回填该日已有内容；记账卡 → 显示并追加到该日
不变化的部分连续记录天数、领域入口、最近动态

第 4 章今日速记区

可配置区块

「今日速记」区放哪几张表单，由设置页勾选决定，默认勾选日记与记账。将来新增"运动打卡"或"睡眠记录"时，只要那张表单已经存在，勾一下它就出现在首页。

这与 PRD 的 DP-01（零硬编码）与 DP-02（声明式表单）是同一条路子：首页放什么，本身也是声明出来的，不是写死的。

日记卡

字段构成沿用 PRD 6.1，共 8 项：

字段标签类型
date日期date（默认所查看日期）
mood心情select：开心 / 平静 / 焦虑 / 疲惫 / 难过 / 兴奋
weather天气text
events今日事件textarea → 正文 ## 今日事件
gains今日收获textarea → 正文 ## 今日收获
regrets今日遗憾textarea → 正文 ## 今日遗憾
tomorrow明日目标textarea → 正文 ## 明日目标
images图片attachment，1–3 张

记账卡

一个可增删的多行明细列表，每行四个控件：金额、分类、账户、备注。底部有「+ 添加一笔」与「保存记账」两个动作。默认显示 1 行空明细，提交后清空复位。

为什么两张卡各自独立保存

关键取舍

日记与记账的触发时机不同：记账发生在消费当下（买完咖啡就想记一笔），日记发生在一天结束（写的时候要回顾一整天）。

如果绑成一次提交，晚上写日记时发现白天漏了三笔账，只能在日记表单里补录——而那一刻你的注意力在"写"上，不在"记"上。把节奏不同的两件事绑成一个动作，长期一定会牺牲掉其中一个。

数据分发

两张卡虽然同处一页，但提交后落到完全不同的文件和结构里：

首页 · 今日速记
   ├─ 日记卡 ──→ 00_时间轴/日记/2026/09-28.md
   │              段落更新（section-update）
   └─ 记账卡 ──→ 10_生活/11_记账/2026-09.md
                  向 frontmatter 的 transactions 数组追加（append-item）

第 5 章领域入口与列表视图

入口形态

四张等重卡片：时间轴 / 生活 / 知识 / 行动。等宽等高，不给任何一方加视觉权重——这是"全生活记录系统"定位在界面上的直接体现。

点击后在插件内的列表视图打开该领域记录，不跳转到 Obsidian 的文件树。理由：系统承诺的是"用户只管填表、结构自己长"，一点入口就把人甩进文件树，这个承诺就破了。

核心概念：条目（item）

列表的"一行"不等于"一个文件"

这是一个必须立起来的概念，因为记账改存数组之后，两种数据形态同时存在：

列表一行 =说明
日记一个文件一天一条
旅游 / 娱乐 / 知识 / 项目一个文件一个实体一条
记账一笔一个文件里可能躺着上百笔，需 FLATTEN 展开

因此回显层的数据模型是「条目（item）列表」，一个文件可以产出 N 个条目。PRD 4.1 中"以列表、看板、统计形式呈现"的表述需补上这一层次。

各领域列表列定义

列表是拿来扫读的，列要少、信息密度要高。建议列如下：

领域条目列
时间轴日记日期 · 心情 · 天气 · 摘要
生活记账明细日期 · 金额 · 分类 · 账户
生活旅游行程 · 目的地 · 起止
生活娱乐作品 · 类型 · 状态 · 评分
知识笔记标题 · 类型 · 分类 · 更新
行动项目项目 · 状态 · 进度 · 截止

筛选与排序

各领域列表共用同一套筛选控件：

时间范围状态分类关键词搜索多列排序

默认按时间倒序排列。

新建入口

列表视图右上角设「新建」按钮；同时在命令面板为每张表单注册独立命令（如「新建旅游记录」）。两个入口并存——列表按钮给浏览场景，命令给键盘操作场景。

第 6 章最近动态

首页最下方是一条跨表单的动态流：只要通过插件表单创建或更新了一条记录，它就出现在这里。默认显示最近 10 条，按更新时间倒序。

与「近期」的区别：从日期轴换到事件轴

这一段原先叫「近期（连续 7 天）」。改名不是措辞调整，而是换了一根组织轴：

维度近期（原设计）最近动态（现设计）
组织轴日期轴——连续的日历日事件轴——提交过的记录
跨表单否，只读日记是，所有已实现表单
空洞无记录的日子淡显「未记录」不出现（只列真实记录）
回答的问题我哪天漏记了我最近记了些什么

换轴的理由：首页是概览层，它要回答的是"现在处于什么状态"。在只有日记一种数据源的阶段，"连续 7 天"是个好答案；但当记账、任务、阅读陆续接入，"最近发生了什么"比"哪几天空着"更贴近概览层的职责。

「一条动态」的粒度

一条动态 = 一个条目（item），与第 5 章定义的条目概念一致：

来源表单一条动态是示例
日记一天一条09-28 09:15 · 日记 · 今日存档已更新
记账一笔一条（非一个月文件一条）09-28 14:32 · 记账 · 餐饮 38.00 · 支付宝
任务一条任务的新建 / 完成09-27 20:11 · 任务 · 完成「整理字段规范」
阅读 / 影视 / 游戏 / 演出一个作品的新建或状态变更09-27 22:40 · 阅读 · 《书名》进度 45%
知识库 / 项目 / 旅游一个实体的新建或更新09-26 19:03 · 项目 · LifeOS 插件 新建
记账为什么按「笔」不按「文件」

月度记账文件是容器，不是记录本身。若按文件粒度，一个月只会出现一条「2026-09 记账已更新」，看不出具体记了什么——而"最近记了什么"正是这条动态流存在的理由。

排序与去重规则

项规则
排序键updated（记录最后修改时间），倒序
计入范围新建 + 更新都计入。改一笔账、补写今天的日记，都会顶到最前
条数默认 10 条，设置页可调
同一对象重复出现同一条记录被反复修改时只保留最新一次，不重复占位
点击行为点击条目进入沉淀层对应详情

空态

尚无任何记录时显示一句引导文案（如「还没有记录，从上面的日记卡开始」），不显示空列表骨架。

DP-10 的去向

一条原则的适用范围收窄，而非失效

DP-10（骨架在视图层，不在文件层）原由"近期 · 连续 7 天"确立。首页改为事件轴后，这条原则从首页撤出——但原则本身依然成立，它约束的是所有以日期为轴的视图（日历热力图、周视图、项目时间线）。

换句话说：首页这次换成了事件轴，日期骨架就不再需要在这里体现；将来做日历视图时，DP-10 照旧适用。

第 7 章记账落盘规格

为什么不用 Markdown 表格

原设计是把每笔账追加成月度文件里的一行表格。问题在于：Dataview 与 Bases 只读 frontmatter，读不到正文里的表格。若沿用表格，"后期分别摘取记账数据做报表"这个需求会直接落空。

因此改为：明细存在 frontmatter 的对象数组里，正文只放渲染块。

文件结构

---
title: 2026年9月记账
type: finance
period: 2026-09
transactions:
  - { date: 2026-09-28, amount: 38.00, category: 餐饮, account: 支付宝, note: 午饭 }
  - { date: 2026-09-28, amount: 12.50, category: 交通, account: 微信 }
  - { date: 2026-09-26, amount: 136.00, category: 购物, account: 银行卡 }
created: 2026-09-01
updated: 2026-09-28
---

# 2026年9月记账

（正文为 Dataview 渲染块，实时呈现下方表格）

路径：10_生活/11_记账/{YYYY-MM}.md；合并方式：append-item（向数组追加一项，mergeMode 的新取值）。

period 字段不可省略——没有它，Dataview 只能靠文件名去匹配月份。

数组字段规范（格式即契约）

原 6.2.1「表格格式锁定」由本节取代。锁定的对象从"表格列"变为"数组键"。

项锁定值
字段名与顺序date → amount → category → account → note，固定不调换
date完整日期 YYYY-MM-DD（不是表格时代的 MM-DD）
amount纯数字，两位小数，恒为正数，不带货币符号、不带千分位
收支方向由 category 是否为「收入」判定，不由 amount 正负表示
category严格取自枚举：餐饮 / 交通 / 购物 / 居住 / 医疗 / 娱乐 / 人情 / 收入 / 其他
account严格取自枚举：支付宝 / 微信 / 银行卡 / 信用卡 / 现金
空值省略该键，不写 null / - / N/A
追加位置数组末尾，不倒序插入
两处需在 PRD 中同步修订

其一，日期格式变了。表格时代是 MM-DD（因为文件名已含年月），数组里必须是完整 YYYY-MM-DD——否则 WHERE t.date = this.date 这类跨文件查询无法成立。

其二，金额恒为正数。原 PRD 6.2 的备注写作"正数，支出为正、收入为负"，表述自相矛盾，且没有定义收支方向的判定字段。现在统一由 category 判定，避免出现有人写 -38、有人写 38 的格式漂移。

删掉的字段

原 6.2 中有 account（支付宝 / 微信 / 银行卡 / 现金）与 payment_method（现金 / 信用卡 / 移动支付）两个字段。两者语义高度重叠——都回答"这笔钱用什么付的"，并存会导致录入时被问两遍，且答案互相打架。

删除 payment_method，只保留 account，取值扩展为：支付宝 / 微信 / 银行卡 / 信用卡 / 现金。这符合 DP-08 单一归属。

防重复提交

采用轻量方案：提交后立即清空表单 + 按钮短暂禁用，YAML 中不增加去重字段。

代价说明：若出现"写入成功但界面无反应"的极端情况，用户重试仍会重复。此时靠 Dataview 渲染块能直观看到重复条目，手工删除即可。

正文的渲染块

月度文件正文放一个 Dataview 代码块，把数组渲染成表格，补偿人读体验：

```dataview
TABLE WITHOUT ID t.date AS 日期, t.amount AS 金额, t.category AS 分类, t.account AS 账户
FROM "10_生活/11_记账"
FLATTEN transactions AS t
WHERE period = "2026-09"
SORT t.date DESC
```

渲染而非存储，不违反 DP-08 单一归属——与日记的「今日汇总」块用的是同一手法。

第 8 章关联机制

日记底部放「今日汇总」块，自动列出当天的每一笔账：

```dataview
TABLE WITHOUT ID t.amount AS 金额, t.category AS 分类, t.account AS 账户
FROM "10_生活/11_记账"
FLATTEN transactions AS t
WHERE t.date = this.date
```

this.date 读的是日记自身的 date 字段。打开任何一天的日记，底部自动出现当天的消费明细——用户不需要做任何关联操作。

项规则
关联方向单向：日记 → 记账
为什么不双向记账文件反过来链接日记会造成互相引用，既冗余又容易出循环
段落性质由插件创建一次，此后不参与表单写入；内容由查询实时生成，不落静态文本

第 9 章附件存储

采用统一附件目录：

90_系统/附件/{YYYY}/{MM}/{date}-{序号}.{扩展名}
例：90_系统/附件/2026/09/2026-09-28-1.jpg
项说明
目录名可配置默认 90_系统/附件，设置页可改（DP-01 零硬编码）
为什么集中便于清点与迁移；重建库时附件不散落各处
已知代价附件与记录分离，删除记录时附件会变成孤立文件——需要在删除时提示用户
不采用全局设置的原因Obsidian 的 attachmentFolderPath 是全局的，改动会影响库中所有其他笔记的附件落点

第 10 章入口与启动行为

项规格
视图位置主工作区标签页（四段结构信息量大，侧边栏会挤变形）
打开方式Ribbon 图标 + 命令面板命令，双入口

DP-11 的措辞

插件只动自己写入的内容。用户在 md 中手工添加的段落、手工修改的字段，插件一律不碰。

这条不是技术约束，是价值约束——这个系统存在的意义是"数据属于你"。如果插件动不动就重写用户的文件，它和一个封闭的 App 就没有区别了。
